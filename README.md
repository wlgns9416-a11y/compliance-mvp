# compliance-mvp — 재개 가능 문서 분석 파이프라인

150페이지 PDF를 올렸는데 텍스트 추출은 성공하고 AI 분석이 중간에 실패했다. 전체 재처리 없이 실패분만 재시도하려면 파이프라인을 어떻게 설계해야 하는가.

이 레포는 그 질문 하나에 답하는 **작동하는 코드**다. 설명이 아니라 실행되는 테스트가 답이다.

**테스트 17/17 통과.**

```
npm test
```

핵심 단언은 `THE CASE` 테스트다 — 재개 시 처리한 청크 수가 실패분과 정확히 일치하고, 이미 완료된 청크가 모델에 재전송된 횟수가 0이다.

**런타임 의존성 0.** 영속화는 Node 22 내장 `node:sqlite` 를 쓴다 — `npm install` 이 아무것도 설치하지 않고 postinstall 스크립트를 실행하는 패키지도 없다. 컴플라이언스 제품의 공급망 표면은 제품의 일부라는 판단이다. 직전 리비전은 `better-sqlite3` 하나 때문에 전이 의존성 **38개**를 끌고 왔고 그중 1개가 설치 스크립트를 실행했다.

## 설계 3항

**⑴ 작업 단위가 청크지 문서가 아니다.** 추출과 분석이 별도 단계로 영속화되고, 청크가 이미 있으면 추출은 no-op이다. 분석 실패가 추출을 무효화할 수 없다.

**⑵ 재시도가 코드 경로가 아니라 쿼리다.** `resume()` 함수가 없다. 워커는 항상 같은 질문만 한다 — claim 가능한 청크를 달라. 첫 실행과 다섯 번째 재시도가 동일한 코드를 탄다. 신선한 문서와 반쯤 실패한 문서가 구분되지 않으므로 재개 로직이 썩을 수 없다.

**⑶ 멱등성이 관례가 아니라 제약이다.** `UNIQUE(chunk_id, rule_id, page_ref)` + `ON CONFLICT DO NOTHING`. 전 청크를 pending으로 되돌리고 재실행해도 finding 수가 동일하다.

## 실측된 결함 1건 (첫 구현)

첫 구현은 **틀렸다.** 실패 청크를 같은 run 안에서 즉시 재claim해 재시도 예산(`attempts < maxAttempts`)을 밀리초 만에 소진시켰고, 두 번째 run에는 살릴 청크가 없었다.

- 술어는 정확했고(`attempts < max`) **그 예산이 run 간에 분배돼야 한다는 결정과 어긋났다**
- 처분 = run당 청크 1회 시도 제한(`skip` 집합) + 지수 백오프(`next_attempt_at`)
- 설명 단계에서는 완결로 들리는 설계가 **실행에서만** 깨진 사례다

## 구조

```
src/schema.sql         Postgres 의미론으로 작성(Supabase 이관 시 타입명만 교체)
src/pipeline.ts        ingest / extractAndChunk / claim / commit / run
src/access.ts          조직·역할(owner/admin/member)·테넌트 격리·사용량 상한
test/pipeline.test.ts  실패 주입 8종 — 난수가 아니라 결정적 함수
test/access.test.ts    테넌트 경계·권한·상한 9종
```

요구 = Node 22.5 이상(`node:sqlite` 내장 시점). 그 외 준비물 없음.

## 아직 없는 것

- 실제 PDF 파싱 (현재는 페이지 배열 주입)
- OpenAI 연결 (현재는 결정적 가짜 분석기 — 파이프라인 검증에는 오히려 이쪽이 옳다)
- 대시보드·결제 · 배포 파이프라인

## 설계 원칙

의존성 0 · 스키마는 Postgres 의미론 · 모든 테넌트 접근이 actor 를 경유. 상세는 각 파일 상단 주석에 있다.
